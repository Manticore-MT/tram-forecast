# tram-forecast

ИИ-прогноз загрузки трамвайных маршрутов (Хакатон Московского транспорта). Команда **Manticore-MT**.

Веб-сервис прогнозирует пассажиропоток по маршрутам (маршрут × час; по остановкам данных нет, поэтому остановочного уровня нет) на четыре горизонта (день, неделя, месяц, год),
показывает диспетчеру отклонение от обычного уровня, зоны внимания и рекомендации, а результат можно
выгрузить в CSV.

> **Статус.** Реализованы ML-сервис FastAPI, backend Spring Boot, PostgreSQL и frontend.
> Production Compose подключает ML по HTTP; обычный локальный Compose может работать в `stub`.
> Подтверждённый командой score конкурсного CSV — **0.89212**; очищенная HTTP-выдача
> и экспериментальная модель внешних факторов имеют отдельные ограничения и метрики.
> Актуальный запуск ML: [ml_readme.md](ml_readme.md).

**Для жюри: критерий 2.** [Источники, проверка эффекта, область адаптации и сценарий демонстрации](ml/CRITERION_2.md).
В «Обзоре» есть блок «Внешние факторы: проверка эффекта»: пять обученных вариантов,
три временные проверки, подписанные положительные/отрицательные эффекты и график
сравнения. Полные метрики: [evidence.json](ml/artifacts/factors/evidence.json).

## Быстрый старт

Нужен Docker.

```bash
docker compose up --build
```

Бэкенд отвечает на <http://localhost:8080>:

```bash
curl http://localhost:8080/actuator/health
curl "http://localhost:8080/api/meta"
curl "http://localhost:8080/api/routes?horizon=day"
```

Без ML-сервиса бэкенд сам отдаёт детерминированные синтетические прогнозы (`modelVersion = "stub"`,
`/api/meta` возвращает `dataSource: "stub"`), чтобы остальное можно было делать и показывать заранее.

## Эндпоинты

| Метод и путь | Что отдаёт |
|---|---|
| `GET /api/meta` | текущий момент, допустимые даты, шаг горизонтов, источник данных (`model` или `stub`) |
| `GET /api/routes` | ряды прогноза по каждому маршруту (для раскраски карты) |
| `GET /api/routes/{routeId}/forecast` | маршрут: базовый уровень, отклонение, статус, пик, рекомендация, факт год назад, факторы модели |
| `GET /api/attention` | зоны внимания по маршрутам (по сумме маршрута, не по остановкам) по убыванию отклонения, с рекомендацией |
| `GET /api/routes/{routeId}/load-matrix` | «типичная неделя»: нагрузка по дню недели и часу |
| `GET /api/model/stats` | качество прогноза: WAPE по исходным прогнозам дня против факта |
| `GET /api/export` | выгрузка прогноза в CSV |

Формальный контракт: [`docs/openapi.json`](docs/openapi.json) (OpenAPI 3.1). Он генерируется из кода, а тест в CI
проверяет, что файл не устарел. Интерактивная документация при запущенном бэкенде:
<http://localhost:8080/swagger-ui.html>.

Общие необязательные параметры: `horizon` (`day` по умолчанию, `month`, `year`), `date` (`YYYY-MM-DD`,
по умолчанию сегодня, не дальше года вперёд), `snapshot` (`latest` или `initial`), поправочные
коэффициенты `weather`, `event`, `season` (0.1–3.0), интервал `from` и `to`. Шаг точек задаётся
горизонтом: день по часам, месяц по дням, год по месяцам. Время везде ISO 8601 со смещением
(`2026-09-25T09:00:00+03:00`). Реальные примеры ответов лежат в [`docs/examples`](docs/examples)
(получены на синтетических данных).

## Как устроено

Гексагональная архитектура, границы слоёв проверяет ArchUnit, Javadoc обязателен (Checkstyle):

- `domain`: модель и чистые правила (отклонение, зоны внимания, WAPE), без фреймворков;
- `application`: сценарии использования, тоже без Spring; собираются в конфигурации инфраструктуры;
- `infrastructure`: Postgres (JDBC, Flyway), клиент ML (HTTP или заглушка), кэш чтения;
- `web`: REST, ошибки в формате RFC 9457.

Ключевые решения:

- **Чтение из хранилища, ML только при пропуске.** Запрос отвечает из сохранённых агрегатов; если их нет,
  бэкенд один раз просит ML, сохраняет ответ и продолжает. Если ML недоступен, но что-то сохранено, отдаётся
  сохранённое, иначе `503` с понятным сообщением.
- **Прогнозы только добавляются.** Каждый пересчёт это новая запись. Поэтому доступен «прогноз, как он был в
  начале дня», а точность честно считается по нему, а не по постоянно меняющемуся прогнозу.
- **Зоны внимания, отклонение и рекомендации считает бэкенд** из базового уровня и прогноза, которые отдаёт ML.
  Пороги (10% и 25%) временные, их надо согласовать.
- **Карта и геометрия на фронте.** Бэкенд оперирует только идентификаторами маршрутов и остановок.
- **Spring MVC, а не WebFlux:** нагрузка это чтение готовых агрегатов, реактивный стек ничего не даёт.

Контракт с ML описан в [`docs/ml-contract.md`](docs/ml-contract.md), заметки для фронтенда в
[`docs/frontend-integration.md`](docs/frontend-integration.md). Режим ML задаёт `TRAM_ML_MODE`
(`stub` или `http`).

## Тесты

```bash
cd backend && ./mvnw test
```

Тесты SQL и проверка контракта идут на настоящем Postgres в контейнере (Testcontainers) и пропускаются, если Docker
недоступен. Если изменились эндпоинты или поля ответов, обновите контракт:
`./mvnw test -Dtest=OpenApiSpecTest -Dopenapi.update=true`.

## Известные ограничения

- Маршрутная история и офлайн-пайплайн подключены. Реальной геопривязки валидаций
  к остановкам и непрерывного обновления фактов нет.
- Цель — успешные валидации по маршруту × час, не фактическая заполненность салона.
  Baseline — историческая медиана; его применимость ограничена режимом движения.
- Выгрузка только в CSV (XLSX нет).
- Замеры производительности будут добавлены после подключения реальных данных.
