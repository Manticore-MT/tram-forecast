## Участок между остановками (сегмент маршрута)

Бриф прямо требует детализацию «по маршруту, остановке/участку» (целевые задачи, требования к API,
критерий 4) — это напомнила Анастасия. `product-decisions.md` (§ "Map interaction") требует, чтобы
перегоны между остановками были кликабельны, как и остановки. Но датасет даёт прогноз только
маршрут × час — источника данных на уровне участка (и даже остановки) нет.

Предложение фронта (Адис, 26.09), **требует подтверждения бэка и ML**: участок — сосед остановки на
одном уровне иерархии (сеть → маршрут → {остановка | участок}), участок = перегон между двумя
соседними остановками. Отдельная ручка, например
`GET /api/routes/{routeId}/segments/{fromStopId}/{toStopId}/forecast` (если принимать произвольную
пару остановок — интервал «от A до B» получается бесплатно).

**Нужно узнать:**

- У ML/Никиты: что такое «загрузка участка» — наполненность вагона на перегоне (вошло минус вышло)?
  Валидации фиксируют только вход — можно ли оценить выходы? Если нет — участок временно считается
  производной от двух соседних остановок (тогда это та же величина, что у остановки).
- У Кирилла: делаем ли ручку для участка, и в какой форме.

**Созвон 27.09: участок добавляем.** На вопросы выше (механика — ручка бэка или сумма на фронте, что
такое «загрузка участка») ответа не было — **остаются открытыми, Кириллу и Никите**. Уточнение от бэка:
значения по остановкам сейчас демонстрационные (прогноз маршрута, поровну разделённый на остановки),
так что сумма по остановкам на фронте смысла пока не имеет.

## stopId бэка vs. код остановки у фронта

`ml-contract.md` подразумевает, что `stopId` в ответах API — id из "датасета остановок, которым
фронт рисует карту". В коде (`StubMlForecastClient`) сейчас `stopId` — чистая заглушка ("R1-S2",
порядковый номер в фейковой сетке маршрутов), реального маппинга на датасет остановок нет.

У фронта раньше (`tram-network.json`) не было вообще никакого id остановки — только название и
координаты. Починили: `scripts/build-tram-network.mjs` терял `stopCode` ("Код остановки" из
датасета организаторов) при сборке, хотя сам код там был. Теперь `stopCode` есть у каждой
остановки в `tram-network.json`.

**Нужно узнать у Кирилла/ML:** когда переходим на реальные (не stub) данные — `stopId` будет
строиться по этому же `stopCode` организаторов, или по другому id? Если по другому — нужен либо
общий id на обеих сторонах, либо матчинг по координатам/названиям (с ручной чисткой, если названия
не совпадут 1-в-1). Без ответа: прогноз/зоны внимания могут отображаться у неправильной остановки
на карте.

**Созвон 27.09:** Никита смотрит коды остановок в `shared/tram-stops.json`. Совпадёт ли `stopId` с
«Кодом остановки» — **ответа пока нет**.

## Данные для экрана «Обзор» (стейкхолдер)

Раскладка «Обзора» собрана по must-have из `product-analysis-full.md` (дашборд стейкхолдера). Часть

**Вопросы Кириллу:**

- Можно ли вернуть факт (`actual`) в `/api/routes`? Сейчас там только `forecast`/`baseline`

**Вопросы Кириллу/Никите:**

  в прогнозе остановки.
- Топ **остановок** по отклонению упирается в сопоставление `stopId` с картой (см. «stopId бэка vs.
  код остановки у фронта») — пока «Обзор» показывает только топ маршрутов.

Вне MVP, без вопросов: индекс бесшовности (US11 — метрика не определена), ВСМ (данных нет).
