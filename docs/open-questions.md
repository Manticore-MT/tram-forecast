# Открытые вопросы

Вопросы, которые пока не решены и требуют уточнения (у Никиты по данным, на созвоне по продукту
и т.д.), в отличие от [`product-decisions.md`](product-decisions.md), где зафиксировано решённое.
Не смешивать: сюда попадает только то, что реально требует чьего-то ответа, а не общие рассуждения.

## ВСМ: данные отсутствуют?

`product-decisions.md` § «ВСМ (high-speed rail) impact» держит фичу под условием: делать её только
если в датасете организаторов реально есть данные по ВСМ. Беглая проверка (grep по README и
`spravochniki` в архиве датасета на «всм»/«высокоскорост») ничего не нашла — но это проверка кода,
не ответ команды или организаторов.

**Нужно узнать/решить:** подтвердить у Никиты (или у оргов) — данных по ВСМ в датасете правда нет,
или они просто не размечены явным словом и лежат под другим названием? От ответа зависит, снимать
ли фичу с MVP-скоупа или нет.

## Виджет для корректирующих коэффициентов

API принимает `weather`, `event`, `season` — непрерывные множители 0.1–3.0, по умолчанию 1 (см.
`frontend-integration.md`). В брифе (критерий 2в) нужно, чтобы их можно было менять в UI и сразу
видеть, как меняется прогноз. Не решено, каким виджетом это делать.

**Нужно решить:** слайдер (наглядно показывает диапазон 0.1–3.0, но неточный ввод) vs. number input/
stepper (точный ввод, но менее интуитивно "покрутить и посмотреть") — или комбинация обоих. Не путать
с `factors` из ответа ML (календарь/погода/события) — это отдельный read-only список того, что модель
уже учла, не крутилка.

## Отображение ошибок в UI

Не решено, как показывать ошибки API/загрузки: общий тост, ведущий в единый виджет-лог всех ошибок,
или ошибка прямо на каждом виджете, который не смог загрузиться.

**Нужно решить:** per-widget логичнее сочетается с требованием оргов "не терять контекст объекта при
детализации" (см. `product-decisions.md` § Organizer constraints) — диспетчер сразу видит, что именно
не загрузилось (карта? конкретная остановка? зона внимания?), не уходя за деталями в отдельный лог.
Общий лог ошибок полезен скорее для дебага, чем для диспетчера. Пока не выбрано ни то ни другое.

## Виджеты на карте (drag & drop, интерактивный список)

Идея — сделать функциональные виджеты на карте, которые можно перетаскивать по UI (расположение на
усмотрение пользователя), а не фиксированные панели. Виджеты — из некоего списка доступных виджетов
для взаимодействия и визуализации (какие именно виджеты в списке — тоже не определено). Пока не
решено, делаем ли это вообще.

**Нужно решить:**

- Это фича MVP или nice-to-have на потом — с учётом дедлайна (27.09 23:59) и того, что drag & drop сам
  по себе не влияет на баллы (см. организационные требования к UI в `product-decisions.md` — там про
  clickable-сегменты и тёмную схему, но не про перетаскиваемость).
- Если делаем — какие конкретно виджеты входят в список (график диапазона? зоны внимания? load-matrix?
  что-то ещё) и различаются ли они по типу — "для взаимодействия" (управление/фильтры) vs. "для
  визуализации" (графики, карточки).

## График для диапазона пассажиропотока

Не решено, стоит ли добавлять отдельный график, визуализирующий диапазон (от–до) пассажиропотока —
пока просто мысль, без решения "да/нет".

**Нужно решить:** нужен ли отдельный график вообще, или диапазон и так читается из уже показанных
базового уровня/прогноза/отклонения. Связано с пунктом "пик → диапазон" ниже — возможно, одно и то же
решение закроет оба вопроса.

## Величина рекомендации ("+1 трамвай" vs "добавить N трамваев")

Сейчас в `product-decisions.md` зафиксирован бинарный сигнал (+1 / без изменений / −1) по порогам
загрузки 80%/40%. Возник вопрос, можно ли считать не бинарный сигнал, а конкретное число трамваев.

**Нужно узнать:** есть ли в датасете организаторов данные о текущем интервале движения / доступном
парке по маршруту? Без этого посчитать "сколько добавить" нельзя — уточнить у Никиты, входит ли это
в данные вообще, до того как проектировать API под это.

## Пик → диапазон

В зонах внимания предложено показывать не точку пика, а диапазон (от–до), в котором нужно обратить
внимание. Пик как точное время остаётся на слайдере в детальном виде остановки.

**Нужно решить:** это чисто визуальное решение (тот же ряд точек, просто по-другому его читаем и
рисуем на фронте) — или это значит, что бэк должен отдавать в `/api/attention` не одну точку пика,
а начало/конец окна как отдельное поле? От ответа зависит, нужно ли менять контракт (`ml-contract.md`,
`openapi.json`) или это чисто фронтовая задача.

## Участок между остановками (сегмент маршрута)

`product-decisions.md` (§ "Map interaction") требует, чтобы сегменты маршрута между остановками были
кликабельны, как и сами остановки. Но ни `ml-contract.md`, ни `openapi.json`, ни тем более датасет
организаторов (прогноз только на уровне маршрут × час, см. `product-decisions.md` § "Organizer
constraints") не дают источника данных на уровне участка — это детализация ниже остановки, а прогноза
даже на уровне остановки нет.

**Нужно решить:** будет ли участок отдельной агрегацией на бэке (новая логика, которую нужно
проектировать заранее, а не по ходу фронта), или это чисто фронтовая интерпретация — например, при
клике на сегмент показывать среднее/большее из двух его концов-маршрутов без нового запроса, раз
данных ниже уровня маршрута в датасете нет вообще. Обсудить с бэком/ML.

## stopId бэка vs. код остановки у фронта

`ml-contract.md` подразумевает, что `stopId` в ответах API — id из "датасета остановок, которым
фронт рисует карту". В коде (`StubMlForecastClient`) сейчас `stopId` — чистая заглушка ("R1-S2",
порядковый номер в фейковой сетке маршрутов), реального маппинга на датасет остановок нет.

У фронта раньше (`tram-network.json`) не было вообще никакого id остановки — только название и
координаты. Починили: `scripts/build-tram-network.mjs` терял `stopCode` ("Код остановки" из
датасета организаторов) при сборке, хотя сам код там был. Теперь `stopCode` есть у каждой
остановки в `tram-network.json`.

**Нужно узнать у Кирилла/ML:** когда переходим на реальные (не stub) данные — `stopId` будет
строиться по этому же `stopCode` организаторов, или по другому id? Если по другому — нужен либо
общий id на обеих сторонах, либо матчинг по координатам/названиям (с ручной чисткой, если названия
не совпадут 1-в-1). Без ответа: прогноз/зоны внимания могут отображаться у неправильной остановки
на карте.
