# Хакатон Московского транспорта — контекст проекта

Роль: фронтенд (Адис). Команда: Кирилл (архитектура/бэк), Никита (ML), Анастасия (продукт), Олег (координация).

## Продукт

ИИ-прогноз пассажиропотока трамвайных маршрутов для ЕДЦ ГУП «Московский метрополитен». Два пользователя: диспетчер (оперативная работа, US1-6) и руководитель/стейкхолдер (стратегия, US7-10).

## Требования хакатона (официальные, из брифа)

- Три горизонта: день (обязателен, почасово), месяц, год (опционально)
- Детализация: маршрут, остановка/участок, интервал времени
- Экспорт прогноза в CSV/XLSX — **не реализовано, добавить**
- Учёт внешних факторов: время суток, день недели, сезонность, погода
- Метрика качества модели на защите — **WAPE-score**, не MAPE (baseline 0.48)
- Критерий 2в: в интерфейсе должна быть возможность менять корректирующие коэффициенты (погода/событие/сезон) и видеть, как меняется прогноз — **пересекается с отменённой US5, стоит поднять снова**
- Стек: Backend Java/Spring Boot/Netty, Frontend React 19+/TS, ML — Python, БД — PostgreSQL/ClickHouse
- README с замерами производительности — обязателен (не моя часть, но команда должна знать)
- Дедлайн загрузки решения — 27 сентября, 23:59 МСК

## Технические решения (зафиксированы)

- **Фронтенд-стек**: Vite, не Next.js (нет SSR/SEO-задач, свой бэк закрывает API routes)
- **Карта**: OSM + Leaflet как рабочий вариант для хакатона (изолирована в одном компоненте `MapCanvas`, свап на Яндекс.Карты дешёвый при необходимости). Атрибуция с флагом Украины убирается через `attributionControl: false`
- **Figma не заводим** — макеты визуально берём из готового кита дизайн-системы, код пишем с нуля под свою архитектуру (кит "assumes too much", сделан до анализа требований)
- **Один экран с drill-down** (сеть → маршрут → остановка), не отдельные разделы/вкладки для диспетчера
- **State management**: URL (search params) для навигационного состояния + React Query для серверного состояния + useState для чисто UI-мелочи. Zustand/Redux — только если реально понадобится, не сейчас
- **Discriminated union** для Selection: `{level:'network'} | {level:'route', routeId} | {level:'stop', routeId, stopId}`

## API-контракт

**Решено:**
- Ресурсные пути, не единый вход с `level=`: `GET /routes`, `GET /routes/{id}/forecast`, `GET /routes/{id}/stops/{stopId}/forecast`
- Весь ряд точек одним запросом (не на каждое движение слайдера)
- Поллинг, не WebSocket
- Шаги ряда: `year` → 12 месяцев, `month` → 28-31 дней, `day` → 24 часа
- US5 (сравнение сценариев базовый/с фактором) отменена — модель даёт один прогноз (но см. пересечение с критерием 2в выше)
- Бэку не нужен API карт (Яндекс/2ГИС) — геоданные из датасета, рендер только на фронте

**Не решено:**
- Формат даты в запросе отдельно от `horizon` — точный вид не подтверждён
- Временная иерархия: клик на месяц открывает дни (вложенность) или год/месяц/день — плоский свитч?
- Механика запроса для "сравнение периодов" (два периода в одном вызове или два вызова)
- История качества прогнозирования — нужен сохранённый исторический прогноз от бэка, не пересчёт задним числом
- Прошлая дата в запросе — что считать "прогнозом" (сохранённый на момент расчёта, не пересчёт сейчас)
- Геометрия маршрута — когда ЕДЦ отдаст реальные координаты трассы (сейчас прямые отрезки между остановками)
- Зоны внимания: агрегировать маршрут одним числом или всегда показывать конкретную остановку с макс. отклонением (концы маршрута могут быть спокойными, середина — нет)
- Структура зон внимания: плоский список миксом (остановки+маршруты) или иерархия — предложение: плоский список, сортировка по значимости отклонения
- Realtime механизм для эмулятора потока данных — бэк отдаёт синхронно по запросу или фронту нужен WS/SSE

## Источники данных

- **data.mos.ru** — готовые датасеты: **60664** (936 маршрутов, JSON/XML/XLSX/CSV без авторизации), **60662** (остановки, есть вкладка "Карта", координаты предположительно в JSON). Основной источник статических данных
- **Яндекс.Карты API** — нет публичного эндпоинта для выгрузки маршрутов/остановок, только point-to-point маршрутизация. Бесплатно 500 запросов/сутки для отрисовки
- **2ГИС Public Transport API** — даёт полную геометрию маршрута в WKT, запасной вариант если геометрии в датасете мало. Платный (MAU-модель, ~200к₽/год за безлимит), демо без точных цифр лимита
- **OSM/Leaflet** — тайлы работают без VPN, есть условия использования (валидный User-Agent, кэш 7 дней, без bulk-скрейпа)

## Фичи вкладки "Обзор" (US7-10, стейкхолдер) — подтверждено командой

**Прогноз по сети**: прогноз за период (US7), долгосрочный прогноз (US8,10), прогнозируемые пики (US7), карта спроса (US8), внешние факторы (US7,10)

**Проблемные места**: зоны внимания рейтинг (US7,8,10), отклонение (US7,10), детализация по маршрутам/остановкам (US8)

**Сравнение периодов** (US8): пассажиропоток между произвольными периодами (месяц/месяц, неделя/неделя) — подтверждено Анастасией, механика UI не спроектирована

**Качество прогноза** (US9, всё подтверждено к реализации):
- Сопоставление факт↔прогноз на графике — есть в ките (синяя/красная линия)
- Показатели качества модели — переименовать в WAPE (не MAPE)
- История качества прогнозирования — зависит от бэка (хранение старых прогнозов)

## Открытые продуктовые вопросы

- **Индекс бесшовности** (предложение Анастасии, не из брифа): композитный показатель 0-100 = 0.5·запас_по_загрузке + 0.3·интервал_движения + 0.2·стабильность. UI должен показывать не только число, но причину изменения ("было 86, стало 68 из-за ВСМ, маршруты №7,12, 18:10-18:40"). Сценарный режим для ВСМ, если реальных данных нет (ручной ввод: время прибытия, поток, доля пересадки). **Ждёт оформления как US от Анастасии — не проектировать UI до этого**
- **Рекомендации по вагонам** (+1/-1 трамвай): нельзя привязывать напрямую к росту спроса на 10-15% — нужно отношение спроса к вместимости (Анастасия). Для полной калибровки нужны: вместимость трамвая, число вагонов на маршруте, интервалы, история решений диспетчеров. Если данных нет — упрощённые пороги с настраиваемым в интерфейсе порогом, помечено как демонстрационная рекомендация
- **Матрица загрузки на все маршруты** (понравилась команде, но неясно назначение сверх списка зон внимания) — тикет на отдельный созвон Никита/Адис/Кирилл

## UI / вайрфреймы

- Три варианта финального лейаута нарисованы (колонки / оверлей поверх карты / панель+таблица снизу) — **голосование ещё не проведено**
- Интерактивный прототип собран на реальных компонентах кита (Card, Badge, Stat, LoadMeter, Tag), карта Leaflet+OSM с реальными координатами — работает локально (публичный tile-сервер иногда банит по User-Agent в среде предпросмотра)
- Компонент выбора даты — несколько неудачных итераций, консенсуса по UI нет. Логика: пресеты день/месяц/год в один клик + возможность раскрыть кастомный диапазон (не отдельный режим-переключатель)
- Промпт агенту на сборку UI-композиции: основа — компоненты кита, shadcn/ui только как резерв для типовых элементов (диалоги, тултипы), стилизованный под токены кита, не как замена

## Матрица «экран → данные от бэка» (Adis's fronend layer)

- Экран с картой (drill-down всё/маршрут/остановка) ← `forecast` (3 уровня), `attention`
- "Обзор" для стейкхолдера ← `model/stats`, `forecast`, `attention`
