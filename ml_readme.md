# ML-сервис трамвайного прогноза

## Что работает

FastAPI обслуживает существующий HTTP-контракт `docs/ml-contract.md`.
Backend отправляет `POST /predict` с `{"horizon":"day","date":"2025-11-01"}`,
получает JSON для сети и сохраняет его в своей PostgreSQL. Веса и профили загружаются
один раз при старте. Переобучения, чтения 60 млн транзакций и внешних HTTP-запросов
при прогнозировании нет. ONNX не используется.

Основа — Ridge-регрессия дневного логарифма валидаций, поправка по недавней истории
и распределение дневного уровня по часам. Рабочая версия переобучена после исключения
технологических валидаций с 00:00:00 до 05:29:59. Сервис использует переносимый
`ml/artifacts/route_model.json`: коэффициенты, intercept, поправки, часовые профили
и baseline. Оригинальная версия сохранена в `ml/reference/original_final.joblib`
и `ml/reference/unfiltered_route_model.json`; платформенный score 0.88220 относится
только к ней. Для новой версии скрытый платформенный score пока неизвестен.
Исполнение pickle при старте HTTP-сервиса не требуется.

## Быстрый запуск

Нужен Python 3.12. Из корня репозитория, PowerShell:

```powershell
py -3.12 -m venv ml/.venv
ml/.venv/Scripts/python -m pip install -r ml/requirements.txt
Set-Location ml
.venv/Scripts/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Открыть http://localhost:8000/docs, затем в `POST /predict` нажать Try it out и ввести:

```json
{"horizon":"day","date":"2025-11-01"}
```

Проверка PowerShell:

```powershell
Invoke-RestMethod http://localhost:8000/health
Invoke-RestMethod http://localhost:8000/predict/routes -Method Post -ContentType application/json -Body '{"horizon":"day","date":"2025-11-01","routeIds":["17"]}'
```

Нативный backend может использовать `TRAM_ML_MODE=http` и
`TRAM_ML_BASE_URL=http://127.0.0.1:8000`. Для backend в Docker и ML на Windows хосте
нужен `http://host.docker.internal:8000` и привязка uvicorn к `0.0.0.0`.

Полная локальная связка Docker, из корня:

```text
docker compose -f docker-compose.yml -f docker-compose.ml.yml up --build
```

Новый overlay добавляет контейнер `ml`, включает HTTP-режим backend и устанавливает
демо-часы backend на 01.11.2025. Исходные dev/prod Compose и deployment workflow
не изменены. ML доступен на http://localhost:8000/docs, backend на localhost:8080.
Frontend запускается обычным способом из его README.

## Production

`docker-compose.prod.yml` запускает образ `ghcr.io/manticore-mt/tram-forecast/ml`
вместе с Postgres, backend, frontend и Caddy. Backend работает в HTTP-режиме,
обращается к `http://ml:8000` и стартует после healthcheck ML. ML не публикует порт
наружу; его артефакт и справочник остановок встроены в образ. CI тестирует ML и
публикует образ с тегами `latest` и SHA коммита. Workflow Deploy входит в GHCR
на время скачивания образов, ждёт готовности контейнеров и проверяет `/health` ML.
Подробный порядок выпуска и ограничения дат — в `deploy/README.md`.

В ML-контейнер read-only подключается `shared/tram-stops.json`. Для автономного
Python-запуска в `ml/network/tram-stops.json` находится его копия на момент сборки.
После изменения сети обновить копию либо задать `ML_NETWORK_PATH` и перезапустить
ML. Хеш сети включён в `modelVersion` остановочного ответа.

## API

| Endpoint | Результат |
| --- | --- |
| `GET /health` | Проверка загруженного сервиса, версия артефакта |
| `GET /metadata` | Область применимости, источники, даты, описание baseline и ограничений |
| `POST /predict` | Контракт backend: routeId, stopId, points, factors |
| `POST /predict/routes` | Реальные прогнозы уровня маршрута до распределения по остановкам |
| `GET /metrics?origin=2025-09-01` | Исторические WAPE/score, показатели по маршрутам и 61 дню |
| `GET /docs` | Swagger для ручной проверки |

Запросы `predict` принимают `horizon`, `date` и необязательный `routeIds`
(массив строк). Backend без `routeIds` получает все девять маршрутов:
`1,7,11,12,17,25,26,28,50`. Неизвестный маршрут, повторный ID, неправильный горизонт,
дата или лишние поля дают HTTP 422. Маршрут 5 в сервисе не поддержан: в платформенном
CSV он заполнен нулями только для полноты ключей и отсутствует в карте этой сети.

| Горизонт | Выбираемый период | Шаг |
| --- | --- | --- |
| day | Запрошенный день | 24 часа |
| week | Семь дней начиная с date, включая date | День |
| month | Весь календарный месяц, содержащий date | День |
| year | Весь календарный год, содержащий date | Месяц |

Неделя/месяц/год — суммы почасовых маршрутных значений. Округление `np.rint`
выполняется на уровне маршрут × час (ближайшее целое, половины к чётному), как в
оригинальном submission. После агрегации повторного округления нет.
`periodStart` и `generatedAt` имеют ISO 8601 offset +03:00. Московское время —
соглашение интерфейса, а не доказательство timezone исходного `tran_date_time`.

## Даты и качество

История заканчивается 31.10.2025. Дата отсечения модели всегда 01.11.2025.
До 31.12.2025 включительно воспроизводится основная конкурсная версия.
01.01–31.12.2026 — разрешённый по умолчанию сценарий экстраполяции старой истории.
Ответ имеет суффикс `-scenario` в modelVersion и предупреждение в factors. Это
не оперативный прогноз 2026 года, платформа его не оценивала. Свежие факты в модель
не поступают. Для актуального сервиса потребуется новый датасет и переобучение.

`ML_ALLOW_SCENARIO=false` запрещает весь период после декабря 2025. Запросы,
период которых частично выходит за разрешённые границы, отклоняются целиком.
Год 2025 отклоняется: его январь–октябрь предшествуют отсечке. Доступен год 2026
как сценарий. Дата 2027, даже если UI позволяет её выбрать, даёт 422.
Существующий Java-клиент превращает любую такую ошибку ML в недоступность;
при отсутствии сохранённых данных backend вернёт 503. Для аккуратного UI команде
backend следует согласовать диапазон `/api/meta` с `/metadata` ML.

На ноябрь–декабрь сохранено исходное допущение об ограничениях маршрута 50 по
выходным: его значения заменяются исторической почасовой медианой этого режима
с 06.09.2025. На 2026 предполагается нормальная работа, без бесконечного продления
ограничения. Эффект окончания ремонта по будущим фактам не проверен.

## Остановки и участки: демонстрационный режим

Обучение использует только цель `route × date × hour`. Остановочных фактов,
распределения высадок и загрузки вагонов нет. Однако существующий backend требует
stopId и суммирует остановки, чтобы получить маршрут.

Поэтому `/predict` делит каждое маршрутное значение и baseline поровну между
остановками данного маршрута из справочника. Для 297 маршрутных остановок возвращает
согласованный JSON. **Это явное демонстрационное допущение для подключения UI,
а не обученный остановочный прогноз.** Оно помечено в modelVersion
(`uniform-stops-demo`) и в каждой записи factors. Не удалять эту маркировку в UI.
Одинаковые значения остановок намеренны: данные не дают оснований выбрать разные веса.

Остановочные значения дробные, их сумма восстанавливает целый маршрутный прогноз
с точностью double. Независимо округлять каждую остановку нельзя: сумма изменится.
`/predict/routes` возвращает исходные маршрутные значения без stopId. Нельзя
дублировать полный маршрутный прогноз на каждой остановке — backend умножит сумму.
Посадки по остановкам и число пассажиров на перегоне требуют разных дополнительных
данных. Процент заполнения салона, пассажиры на конкретном рейсе и интервалы
неопределённости не выдаются. WAPE-score маршрутов не распространяется на остановки.

## Baseline и коэффициенты

Baseline — историческая медиана за 56 дней перед 01.11.2025 (06.09–31.10), отдельно
для маршрута, эффективного дня недели и часа. Рабочие дни сохраняют номер дня
недели; рабочая суббота относится к пятнице, обычная суббота к субботе, праздники
и воскресенья к воскресенью. При отсутствии группы берётся медиана того же
маршрута/часа за те же 56 дней, затем 0. Это определение зафиксировано для всех
запросов; будущие факты для него не используются.

Пропущенные группы в исходной полной сетке приняты за 0, как в исследовании.
В рабочем артефакте часы 00:00–04:59 равны нулю, а метка часа 05:00 содержит
только пассажирские валидации 05:30–05:59. Это же правило применяется к baseline.
Из baseline ограничения движения не удаляются: это «типичный наблюдаемый уровень
последних восьми недель», а не спрос при полностью работающем маршруте. Для
маршрута 50 выходной baseline поэтому может быть близок к нулю. Деление на нулевой
baseline в UI должно обрабатываться отдельно. Не путать это окно 56 дней с
поправкой Ridge по последним 28 дням и горизонтом прогноза 61 день.

Исторические почасовые метки лежат в `ml/data/` как CSV; сырые 62,4 млн транзакций
в репозиторий и БД не загружаются. Рассчитанные медианы baseline хранятся в
`ml/artifacts/route_model.json` (`baseline56`) и читаются при запуске сервиса.
Backend получает baseline рядом с прогнозом в JSON и сохраняет свои прогнозные
снимки в PostgreSQL. Baseline сейчас **заморожен на истории до 31.10.2025**;
для постоянной эксплуатации его нужно пересчитывать по новым фактам.

В финальной модели включены календарь, летний период, часовой профиль и недавняя
поправка. Погода и массовые мероприятия выключены. Weather/event/season из
пользовательских настроек уже перемножаются Java backend, ML их второй раз не
применяет. Такие изменения — сценарий пользователя, не измеренный причинный эффект.
Baseline при сценарных поправках остаётся исходным.

Ремонт и перекрытия не подаются в Ridge как числовые признаки. Из дневного обучения
исключены известные периоды ограничений маршрутов 7 и 50: 10.07–06.08.2025 и
выходные с 06.09.2025. Для маршрута 50 на выходные до конца 2025 дополнительно
используется исторический профиль закрытия. Это ручные правила по известным
изменениям движения, а не модель, обученная на полном архиве ремонтов. Новые
ремонты сервис самостоятельно не обнаруживает.

## Метрики и факты

`/metrics` считает WAPE из сохранённых независимых по времени прогнозов, округляя
каждую почасовую точку. Доступны origin=2025-07-01 и 2025-09-01:

| Origin | WAPE | Score |
| --- | --- | --- |
| 2025-07-01 | 0.183907263 | 0.816092737 |
| 2025-09-01 | 0.110913469 | 0.889086531 |

На тех же отфильтрованных фактах прежняя модель получила 0.810852458 и 0.885147184
соответственно. Так сравниваются одинаковые цели; старые и новые исторические score,
посчитанные на разных фактах, напрямую несопоставимы. Эти блоки использовались при
выборе гиперпараметров, поэтому не являются нетронутым финальным тестом. Платформенный
score новой версии нужно получить отдельной отправкой; скрытого факта у нас нет.
Если эталон платформы всё же сохраняет ночные технологические записи, новая версия
на исходных метках получает 0.812514946 и 0.886474252 против 0.815385719 и
0.888576180 у прежней. Это ожидаемый конфликт определения цели, который нельзя
разрешить по открытым данным: нужно уточнение организаторов либо новая отправка.
Отправка `submission_filtered.csv` дала 0.87962 (сообщено командой). Для проверки
гипотезы о ночной части подготовлен отдельный `submission_hybrid_candidate.csv`:
часы 00–05 из прежнего конкурсного файла, часы 06–23 из очищенной модели.
Его результат на платформе — **0.88226** (сообщено командой 26.09.2026).
На исходных метках исторический score такого гибрида — 0.815660372 (июль–август)
и 0.888708212 (сентябрь–октябрь) против 0.815385719 и 0.888576180 у прежней модели.
Это **только конкурсный кандидат**: ночные технологические валидации не являются
пассажирским спросом и не возвращаются ML-сервисом как прогноз загрузки.
Дневные ошибки доступны для построения 30-дневных графиков внутри блока. Суммарный
WAPE надо считать через сумму абсолютных ошибок / сумму фактов, не усреднять
дневные проценты. Непрерывной 90-дневной истории ошибки нет.

Таблица backend `actual_value` рассчитана на факты по остановкам. В этой поставке
она намеренно не заполняется искусственными числами. `/api/model/stats` backend
не подключается к ML `/metrics` автоматически: frontend/backend может использовать
этот endpoint явно или импортировать проверенные маршрутные метрики отдельным путём.
Демонстрационные stop-level actuals не следует выдавать за наблюдения организаторов.

## Эксперимент: дополнительные погодные факторы

В `ml/data/weather_2025_open_meteo.json` сохранены ежедневные температура,
осадки, снег и максимальная скорость ветра для Москвы (55.782074, 37.576374)
за январь–декабрь 2025. Данные получены через [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api)
(`https://archive-api.open-meteo.com/v1/archive?latitude=55.782074&longitude=37.576374&start_date=2025-01-01&end_date=2025-12-31&daily=temperature_2m_mean,precipitation_sum,snowfall_sum,wind_speed_10m_max&timezone=Europe%2FMoscow`).
Для безопасного по времени варианта в `ml/data/weather_climate_2015_2024.json`
есть климатические средние по дню года из того же источника за 2015–2024
(`https://archive-api.open-meteo.com/v1/archive?latitude=55.782074&longitude=37.576374&start_date=2015-01-01&end_date=2024-12-31&daily=temperature_2m_mean,precipitation_sum&timezone=Europe%2FMoscow`).
Оба файла нужны для воспроизведения; внешних API-вызовов при инференсе сейчас нет.

`ml/external_factor_experiment.py` обучает Ridge заново на прежних календарных
признаках плюс погодные признаки и проверяет те же 61-дневные блоки и метки.
`observed` означает фактическую погоду **целевого периода**, известную теперь
ретроспективно, но неизвестную в исходной точке прогноза. `climate` подставляет
климатическое среднее, которое можно знать заранее. Это разные сценарии оценки.
Сохранены все результаты и варианты регуляризации в
`ml/reference/external_factor_experiment.json`. При alpha=1 получено:

| Признаки / погодный сценарий | Июль–август | Сентябрь–октябрь |
| --- | ---: | ---: |
| Исходный Ridge без погоды | 0.816093 | 0.889087 |
| Температура + осадки / observed | 0.813667 | 0.884793 |
| Температура + осадки / climate | 0.817938 | 0.883898 |
| Температура, осадки, снег, ветер, экстремумы / observed | 0.811181 | 0.883980 |
| Температура + осадки с эффектом по маршрутам / observed | 0.815729 | 0.884003 |

Таким образом, дополнительная погода **пока не дала устойчивого улучшения**.
Никакой из этих вариантов не заменяет конкурсный файл с платформенным 0.88226
или рабочий артефакт. Исторические блоки участвовали в подборе, независимым
финальным тестом не являются. Если правила соревнования допускают фактическую
погоду ноября–декабря 2025, её можно использовать для отдельной конкурсной
проверки, но такой результат нельзя описывать как 61-дневный прогноз из
31.10.2025. Сведения об этом допуске получены от команды, письменное правило
организаторов в репозитории не найдено.

Для отдельной проверки на платформе создан **экспериментальный**
`ml/reference/submission_weather_candidate.csv`. Он использует фактические
температуру и осадки ноября–декабря 2025 в дневных часах 06–23 девяти
обученных маршрутов; ночные часы 00–05 и маршрут 5 остаются из
`submission_hybrid_candidate.csv` с подтверждённым score 0.88226.
Все 14 640 ключей сохранены, предсказания неотрицательны. Платформенный score
погодного кандидата **ещё неизвестен**; из-за ухудшения осеннего бэктеста
он не включён в `/predict` и не заменяет рабочий файл. Отправка на платформу
имеет смысл только как отдельный эксперимент при подтверждённом разрешении
использовать ретроспективную погоду целевого периода.

Запуск из `ml/` после установки `requirements-dev.txt`:

```powershell
python external_factor_experiment.py --labels data/labels_day_filtered_all.csv --weather data/weather_2025_open_meteo.json --climate data/weather_climate_2015_2024.json --output reference/external_factor_experiment.json
python export_weather_candidate.py --labels data/labels_day_filtered_all.csv --weather data/weather_2025_open_meteo.json --climate data/weather_climate_2015_2024.json --template reference/submission_hybrid_candidate.csv --output reference/submission_weather_candidate.csv
```

Следующий кандидат — опубликованные заранее изменения движения по конкретным
маршрутам. Например, [изменение 7/50 с 10 июля](https://transport.mos.ru/mostrans/all_news/125272)
объявлено 9 июля, а [выходное ограничение с 6 сентября](https://t.me/s/DtOperativno/22627)
анонсировано после 1 сентября. Поэтому эти сведения **нельзя** подставлять
в бэктесты с отсечками 1 июля и 1 сентября соответственно: это утечка
информации из будущего. Для этого фактора сначала нужен датированный архив
объявлений и отдельная проверка по времени публикации.

## Эксперимент: длина маршрутной поправки и доступность расписания

Рабочая модель **не использует расписание**: в `feature_row` есть маршрут и
календарь, но нет интервала движения, количества рейсов или часов отправления.
В приложенном организаторами справочнике лист `Расписание` содержит лишь 15
остановок одного рейса маршрута 1 (06:53–07:11), а лист `Наряд` — пример на
08.02.2026. Это не полный исторический ряд по девяти маршрутам. Официальный
[сайт расписаний](https://transport.mos.ru/transport/schedule) публикует текущие
интервалы; открытый [GTFS-каталог](https://mobilitydatabase.org/feeds/gtfs/mdb-3226)
показывает снимок 2026 года. Исторический архив расписаний, действовавших на
датах бэктеста и на 01.11.2025, пока не подтверждён. Текущий снимок нельзя
подставить к прошлым датам и называть проверкой влияния расписания.

Вместо неподтверждённого расписания `correction_window_experiment.py` проверяет
периоды 7/14/28/56 дней и среднее/медиану остатка Ridge по маршруту. Во всех
случаях обучение ограничено датой начала 61-дневного блока; часовой профиль и
остальные признаки совпадают с исходным Ridge. Полная таблица — в
`reference/correction_window_experiment.json`:

| Маршрутная поправка | Июль–август | Сентябрь–октябрь |
| --- | ---: | ---: |
| Медиана 28 дней (рабочий вариант) | 0.816093 | 0.889087 |
| Среднее 14 дней | **0.834833** | **0.890392** |

Это улучшение **на двух использованных при подборе блоках**, а не независимая
оценка скрытого теста. Для проверки на платформе создан отдельный
`reference/submission_correction14_candidate.csv`. Он сохраняет ключи, ночные
часы и маршрут 5 из подтверждённого гибрида 0.88226; меняет только дневные
прогнозы девяти обученных маршрутов. До платформенной проверки он не заменяет
лучший файл или рабочий `/predict`.

`GET /metrics` теперь сообщает `platform.score=0.88226` как результат именно
`reference/submission_hybrid_candidate.csv` и выставляет
`servingModelMatchesSubmission=false`: рабочий JSON-артефакт в `/predict`
не идентичен конкурсному гибридному CSV. Предыдущий 0.88220 сохранён отдельно.

## Файлы и воспроизведение

- `app/engine.py`: календарь, порядок признаков и инференс по JSON.
- `app/main.py`: FastAPI, диапазоны дат, агрегация, baseline, остановочный адаптер и метрики.
- `artifacts/route_model.json`: рабочий артефакт с происхождением и параметрами.
- `network/tram-stops.json`: копия карты; в Compose используется общий справочник.
- `reference/original_final.joblib`: исходный обученный объект для архива.
- `reference/unfiltered_route_model.json`, `submission.csv`: прежняя модель и конкурсный результат.
- `reference/submission_filtered.csv`: новый кандидат для отправки на платформу
  (10 маршрутов, 61 день, 14 640 строк; ночные часы 00–04 равны 0).
- `reference/submission_hybrid_candidate.csv`: конкурсная проверка ночной гипотезы;
  отдельно от прогноза пассажирского спроса в API.
- `reference/final_backtest_*.csv`: исторические проверки прежней модели и нефильтрованной цели.
- `reference/filtered_backtest_*.csv`: проверки рабочей модели по фильтрованной цели.
- `reference/final_metrics.csv`, `metrics_by_route.csv`: сохранённые результаты исследования.
- `data/labels_day_train.csv`, `labels_day_test.csv`: неизменённые агрегаты организаторов.
- `data/labels_day_filtered_all.csv`: метки после удаления 265 030 ночных записей.
- `filter_night_labels.py`: потоковый проход по сырым train/test с точной границей 05:30;
  проверяет суммы часов 00–05 по исходным меткам до записи результата.
- `build_artifact.py`: экспорт доверенного joblib в JSON.
- `train.py`: воспроизведение рабочей модели из отфильтрованных меток.
- `backtest_filtered.py`: оценка 61-дневных периодов с отсечкой истории по origin.
- `export_submission.py`: выгрузка рабочего артефакта в конкурсный CSV.
- `export_submission_hybrid.py`: воспроизводимая сборка конкурсного гибрида.
- `tests/test_service.py`: контракт, эталонные прогнозы, агрегация, даты и воспроизведение обучения.
- `benchmark.py`: воспроизводимый локальный замер HTTP-адаптера.

Из `ml/`, с Python dev-окружением:

```text
python -m pip install -r requirements-dev.txt
python filter_night_labels.py --raw PATH_TO_DATASET/train.csv PATH_TO_DATASET/test.csv --labels data/labels_day_train.csv data/labels_day_test.csv --output data/labels_day_filtered_all.csv
python build_artifact.py --source-joblib reference/original_final.joblib --output artifacts/exported_model.json
python train.py --labels data/labels_day_filtered_all.csv --output artifacts/retrained_model.json
python export_submission.py --output reference/submission_filtered.csv
python -m pytest -q
python benchmark.py
```

Joblib открывать только из доверенного источника. Рабочий JSON уже поставлен,
переобучение перед первым запуском не нужно. `train.py` фиксирует исходную отсечку
и конфигурацию; он не обещает автоматического обновления модели на новые периоды.

Исходные labels сохраняют 57 551 строку, а фильтрованные — 51 765; полная сетка
содержит 65 664 строки. Для повторной точной фильтрации нужны исходные сырые CSV:
готовые почасовые метки не разделяют 05:00–05:29 и 05:30–05:59.
Из обучения дневной регрессии исключаются слишком малые значения и известные
ограничения; оценка backtest включает все 24 часа с нулями до 05:00. Коэффициенты учатся на log1p
дневных сумм с alpha=1, поправка — медиана остатков в логарифмах последних 28 дней.
Профиль часов — 80% сезонного и 20% недавнего (56 дней), нормализован до суммы 1.

## Проверка и производительность

Тесты проверяют нули 00:00–04:59 в 13 176 точках ноября–декабря, точную
границу 05:30 на синтетическом примере и воспроизведение модели из фильтрованных меток.
Сумма остановочных долей сохраняет маршрут; дневные, недельные и месячные суммы
согласованы. Проверяются 2026-сценарий, рабочая суббота, неверные даты и маршруты.

Числа локального замера находятся в `ml/reference/local_benchmark.json` вместе
с описанием окружения и метода. Это последовательный FastAPI TestClient, включает
сериализацию ответа, но не TCP, сеть, Docker и параллельную нагрузку. Нельзя выдавать
их за p95 или сотни RPS продакшен-сервиса. Docker daemon в среде разработки на
момент сборки недоступен; контейнерный прогон требует работающего Docker Desktop.

## Источники

### Эксперименты 27 сентября: фактические внешние данные

По подтверждению команды организаторы разрешают все внешние данные целевого
периода, включая фактическую погоду и сообщения о движении. Это ретроспективный
соревновательный сценарий, не прогноз с информацией, доступной на 1 ноября.
Для эксплуатации понадобятся прогноз погоды, известные планы работ и отдельная
проверка качества без знания будущих событий.

Подтверждённые командой результаты платформы: лучший hybrid — **0.88226**,
weather candidate — **0.88080**, correction14 candidate — **0.88046**.
Ни один из двух последних кандидатов не заменяет лучший submission.

**Новый отдельный кандидат:** `ml/reference/submission_service_dates_candidate.csv`.
Воспроизведение: из `ml` выполнить `python export_service_candidate.py`.
Исходный `submission_hybrid_candidate.csv` и production-артефакт не изменяются.
Скрипт проверяет точное совпадение восстановленной дневной модели с champion,
уникальность 14 640 ключей и неотрицательность значений. Меняются только 252 точки:
маршрут 50, выходные с 15 ноября, часы 06–23. Возвращается обычный модельный
профиль вместо профиля закрытого маршрута; суммарная разница +152 103 посадки.
Ночные значения сохранены для изоляции эффекта. Маршрут 7 пока не корректируется.
Команда сообщила результат платформы **0.89174** (27 сентября): прирост
0.00948 относительно 0.88226. Это текущий лучший submission. Production-модель
не заменена; `/metrics` честно сохраняет `servingModelMatchesSubmission=false`.
Полный реестр источников и их фактического участия: [ml/FACTORS.md](ml/FACTORS.md).

Основание — официальное восстановление обычных маршрутов 7 и 50 по выходным
с 15 ноября: https://t.me/DtOperativno/23565 . Начало ограничений:
https://t.me/DtOperativno/22627 . Ранее модель ошибочно продолжала режим закрытия
50-го до конца декабря. Машиночитаемый аудит изменений лежит рядом с CSV в JSON.

`hourly_factor_experiment.py` проверяет нормализованный почасовой CatBoost и
фиксированную смесь 20% CatBoost + 80% Ridge. На четырёх 61-дневных окнах
(начала 1 мая, 1 июля, 1 августа, 1 сентября) чистый CatBoost не дал устойчивого
преимущества. Например, календарная смесь дала соответственно
0.83531 / 0.81490 / 0.87818 / 0.88967 против Ridge hybrid
0.83471 / 0.81566 / 0.87712 / 0.88871. Это локальные backtest-результаты,
не независимый тест после подбора и не score платформы.
Погодные признаки: аномалия температуры, осадки, снег, ветер, осадки за 3/6 часов.
Добавление погоды не гарантирует улучшения на каждом окне.

**Дорожный трафик:** `collect_traffic_reports.py` извлекает скорость потока и
баллы загруженности из публичного официального канала ЦОДД/Дептранса
https://t.me/s/DtOperativno . В `ml/data/traffic_reports_2025_deptrans.json`
у каждой записи есть время публикации и ссылка на первоисточник. Время исходника
UTC; для соединения с маршрутными часами требуется Europe/Moscow. Это редкие
общегородские сводки, а не непрерывная история каждого дорожного участка.
Пропуски означают отсутствие наблюдения, не нулевые пробки. Эти признаки пока
**не обучены и не включены в новый submission**: необходим отдельный backtest.
Публичная доступность сообщений не означает открытую лицензию на весь текст;
сохраняются числовые факты и ссылки, не републикуется полный архив сообщений.

Четыре рассматриваемые категории: календарь, погода, режим движения/ремонты,
дорожный трафик. Нельзя представлять все четыре как уже улучшающие рабочую модель.
